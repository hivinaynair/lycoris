# ERC-4337 in Settle Kit

Adding account abstraction to the SDK and rebuilding the public checkout demo on
top of it. The SDK is the deliverable; the demo exists to prove the SDK's seams
are real.

## The claim

`PaymentSigner` is three methods because the host owns its wallet stack. ERC-4337
is a genuinely different execution model — different submission, different hash,
different failure mode. If it drops in without changing the public surface, the
design is proven rather than asserted.

Ship it as two commits:

1. **4337 absorbed, surface untouched.** The smart account satisfies
   `PaymentSigner`; `type-tests` is unchanged except for one rename.
2. **What correctness forced.** `SettleAdapter.id` and `Quote.method` widen off
   the `"usdc"` literal, and the 4337 receipt client graduates into the package.

The second commit's message is the point: a type surface should change because
correctness demanded it, not because a feature arrived.

## What 4337 is and is not solving here

"Own wallet vs sponsored" is two axes, not one:

| | own gas | sponsored gas |
| --- | --- | --- |
| **own USDC** | today's EOA checkout | the 4337 cell |
| **someone else's USDC** | — | today's CDP wallet (delegation, not sponsorship) |

The agent path already sits in the 4337 cell *without* 4337 — x402's
`ExactEvmScheme` is EIP-3009 `transferWithAuthorization`, and the facilitator
pays gas. So gas is not the argument. The argument is that the account becomes
programmable: atomic batching, session keys, an agent mandate the account itself
enforces.

The SDK exposes `self` and `sponsored-gas`. Delegation stays demo-only glue —
it is the demo's faucet, not a payment mode, and it does not belong in the
public types.

### Blocker, recorded

Base Sepolia USDC's implementation (`0xd74cc5d436923b8ba2c179b4bca2841d8a52c5b5`)
contains no ERC-1271 selector (`1626ba7e`) in its deployed bytecode. Contract
wallets therefore cannot sign EIP-3009 on that token, and a 4337 account cannot
pay through x402's exact scheme on this chain. The agent path stays on an EOA.
Confirm with a live call before relying on this.

## SDK changes

### Commit 1 — rename only

`TxHash` becomes `SettlementHash`, with `export type TxHash = SettlementHash`
retained. This is **not breaking**: `declare const brand: unique symbol` in
`types.ts` is module-local and never exported, so no external code can construct
a brand, and the alias makes the two types identical. Minor bump.

The brand's stated job — "a transaction hash can never land in a payee
position" — was always about not confusing hashes with addresses, and still
holds. Only the name was too narrow.

Receipts to update: `hex-brands.test-d.ts` (alias identity) and
`public-surface.test-d.ts` (exported names).

Nothing else in `packages/` moves. That is the claim.

### Commit 2 — what correctness forced

`SettleAdapter.id` is typed `"usdc"`. `Quote.method` is typed `"usdc"`. So
`methods: SettleAdapter[]` and `selectMethod(id: string)` are decorative today —
the array can only ever hold one element. The design anticipated plurality and
the types never delivered it.

4337 is the first real second method. Widen both, add
`createSmartAccountUsdcMethod()` with `id: "usdc-4337"`, and `selectMethod`
means something for the first time.

The 4337 receipt client graduates into a **subpath export** so core's main
bundle stays free of account-abstraction code. Enforce it the way agent code is
already enforced: `measure-settle-kit.mjs` throws on `includesAgentSdk` with
"Agent code leaked into checkout" — add the same assertion for
`viem/account-abstraction`.

The settlement identifier also stops being one opaque hash. Use mutual
exclusion, not a branded union:

```ts
type Settlement =
  | { transactionHash: SettlementHash; userOpHash?: never }
  | { userOpHash: SettlementHash; transactionHash?: never };
```

This narrows on field presence with no runtime tag, and the `?: never` arms make
the two shapes statically incompatible. A branded union cannot do this — see
Rejected.

## The correctness core

A userOp bundled into a **successful** transaction can still have reverted.
Today's `confirm()` returns `receipt.status`, which is the *bundle's* status:

```ts
const receipt = await client.waitForTransactionReceipt({ hash: txHash, ... });
return receipt.status;   // "success" for a bundle whose userOp reverted
```

That would mark an unpaid purchase as settled. It is the standard 4337 tell and
the first thing a reviewer will look for.

The fix needs no core change in commit 1, because the seam already exists.
`UsdcMethodOptions.receiptClient` is injectable and its shape is exactly right:

```ts
waitForTransactionReceipt: (args: { hash; confirmations; timeout })
  => Promise<{ status: "success" | "reverted"; transactionHash }>
```

A 4337-aware client calls `eth_getUserOperationReceipt`, reads
`UserOperationEvent.success`, and returns `"reverted"` when the userOp failed
inside a successful bundle.

**Failure semantics.** The signer returns the userOpHash even when the userOp
reverts. State goes `settling` → `confirm()` → `"reverted"` → `failed` with the
hash populated — the identical path a reverted ERC-20 transfer takes today. That
symmetry is the evidence the abstraction holds. A signer that threw instead
would create a second failure route, and `SettleKitError` carries only `code`
and `message`, so the hash would be lost and `CheckoutState.failed`'s optional
`txHash` slot would sit empty.

### Errors gain a docs channel

`SettleKitError extends Error` with `code` and `message` and nothing else, so a
submission failure that *has* a hash has nowhere to put it.

Rebase it on viem's `BaseError`. viem is already a peer dependency and core
already imports `encodeFunctionData`, so this costs no new dependency:

```ts
export class SettleKitError extends BaseError {
  constructor(code: SettleErrorCode, message: string, options?: { docsPath?: string }) { ... }
}
```

That brings `docsPath`, `shortMessage` and `metaMessages` for free, and gives
the hash somewhere to live.

Two things to watch. `instanceof Error` and `.code` both survive, but `BaseError`
composes `.message` differently — and `toSettleError` reads `.message` to detect
wallet rejection, so its string matching needs a pass. And `measure-settle-kit.mjs`
will register the size delta; check it stays inside budget.

Its own commit, before or after the 4337 work. Not smuggled into either.

## Demo changes

One checkout path. The throwing stub signer in `sponsored-payment.ts` —
`address: recipient`, `sendTransaction` that throws — is deleted, and with it
the `settle` override that makes the demo bypass the SDK's own balance preflight.

### Burner smart account

`generatePrivateKey()` into localStorage, `toCoinbaseSmartAccount`, counterfactual
address. No connect, no sign-in: the visitor never sees a wallet, which preserves
the README's zero-friction promise.

`toCoinbaseSmartAccount` pins **EntryPoint 0.6** in viem 2.56.3
(`toSoladySmartAccount` is 0.7, `toSimple7702SmartAccount` is 0.8/0.9). 0.6 is
dated and chosen deliberately: it is Base's canonical account and what CDP's
bundler and paymaster are built around. Comment the choice in the code.

### Key storage threat model

localStorage is XSS-readable. What the key controls is 0.1 *test* USDC on a
testnet. The asset worth protecting is the paymaster, and the key does not guard
it — the paymaster policy does. With the proxy validating "USDC `transfer`, to
the merchant, exactly `WEATHER_AMOUNT_ATOMIC`," a stolen key lets an attacker
sign a userOp that pays the merchant.

The real abuse surface is the faucet route: mint burner addresses in a loop and
drain the cap. That is rate limiting, and it is independent of key storage.

A key JavaScript can use is a key XSS can use. IndexedDB, sessionStorage and
encryption-at-rest are theater. The only real hardening is a credential the page
can invoke but never read — `createWebAuthnCredential` / `toWebAuthnAccount`,
which `toCoinbaseSmartAccount` accepts as an owner. Not taken: a biometric prompt
is the signup the README promises there isn't.

**This pattern must not leave `apps/lycoris`.** A host copying a localStorage
private key with real money has a genuine vulnerability. Say so in the docs.

### Funding

USDC must reach a counterfactual address before the userOp. Fund inside the
`settle` override, before delegating:

```ts
async settle(input) {
  await fundBurner(input.quote.requestId, input.signer.address);
  return method.settle(input);   // preflight now verifies the funding landed
}
```

Budget slots get consumed by intent rather than curiosity — funding on `quote()`
would burn a slot on every page load, since `selectMethod` runs on mount. The
faucet route must wait for its own receipt before returning or `balanceOf` reads
stale (~2s on Base).

The side effect is the prize: `createUsdcMethod`'s balance preflight stops being
ceremony and becomes the assertion that funding landed. AGENTS.md says not to
skip that preflight; this is the first time it earns its keep.

### Paymaster and bundler

Two endpoints, different risk. The **bundler** relays a signed userOp — direct
from the browser. The **paymaster** spends money — proxied through
`/api/paymaster`, which holds the secret and rejects any userOp that is not a
USDC `transfer` to the merchant for the exact amount.

A domain allowlist is an `Origin` header, which curl forges in one flag. A
paymaster URL in a client bundle is a public faucet with your name on it.

Express the sponsorship rule as data rather than an `if` buried in the handler,
so the policy is reviewable at a glance and testable without the route:

```ts
const sponsorship = {
  calls: [{ to: BASE_SEPOLIA_USDC_ADDRESS, selector: "transfer", args: [MERCHANT, AMOUNT] }],
  rateLimit: { count: 10, scope: "total" },
};
```

The route's only job is to validate the decoded userOp against this object.

### Database

`reserve_sponsored_checkout` holds up unchanged — advisory lock, cap of 10,
idempotent by purchase id, failed slots stay consumed. It reserves budget, not a
transaction, so it does not care that the payer changed.

A purchase is now two on-chain events (sponsor → burner faucet, burner → merchant
userOp), so `tx_hash` splits into `funding_tx_hash` and `user_op_hash` or the
column starts lying. Sponsor outflow per purchase is unchanged at 0.1, so the
budget math survives.

### Explorer links

The signer returns a userOpHash, which Basescan's `/tx/` will not resolve.
`checkout.tsx` already takes `transactionUrl` as an overridable prop — the SDK
anticipated this. `merchant-checkout.tsx` hardcodes `` `/tx/${txHash}` `` instead
of using the escape hatch; fix it to pass the prop.

## No wagmi

Not in the SDK, not in the demo. `settle-kit-boundaries.test.ts` asserts
`require("wagmi")` is rejected, and the design doc lists it as forbidden. The
burner needs no wallet library at all — a local key plus `toCoinbaseSmartAccount`
is the whole thing.

Interop is demonstrated by a documented adapter rather than a dependency — see
Docs below.

## Docs

### Writing a `PaymentSigner`

The SDK's entire pitch is that the host owns its wallet stack, and there is
currently no page explaining how to write the three methods. That page is the
thesis, so it ships with this work. Three worked adapters, one short section
each:

```ts
// wagmi
export const wagmiSigner = (client: WalletClient): PaymentSigner => ({
  address: client.account.address,
  sendTransaction: (tx) => client.sendTransaction({ ...tx, account: client.account, chain: null }),
  getChainId: () => client.getChainId(),
});
```

Plus a bare viem `walletClient`, and the CDP server wallet. Each one turns "no
wagmi" from a limitation into a demonstrated claim.

### Machine-readable docs

Serve `llms.txt` and expose each docs route as markdown. For a repo whose thesis
is *agentic* payments, docs an agent can consume is the argument made twice —
and it is close to free, since the docs pages are already MDX-shaped content.

## Testing

No live bundler required. `createUsdcMethod` already injects `client` and
`receiptClient`, so the case that matters is a plain unit test with a fake
receipt:

> bundle status `success`, `UserOperationEvent.success: false` → `confirm()`
> must return `"reverted"`.

That test is the most convincing file in the changeset.

Existing gates still apply: `bun run check-types && bun run check-boundaries &&
bun run check-tokens && bun test`.

## Costs, stated

- **Economically nothing changes.** The sponsor still supplies the USDC. What
  changes is that the demo runs the SDK's real path instead of routing around it.
- **One click becomes fund → deploy → pay, roughly 5 seconds.** Three labelled
  states read as a payment system doing work, and they are the only view of 4337
  the page offers — but it is genuinely less snappy.
- **EntryPoint 0.6 is dated.** Deliberate; see above.
- **~150 net new lines** in `apps/lycoris`, and a deletion in the SDK's favour.

## Future work: the mandate as account policy

Today the AP2 mandate is an off-chain signature that a trusted facilitator
checks. The same constraint expressed as account-level policy — a session key
that may only call USDC `transfer`, only to a known merchant, only up to an
amount, only within a window, only at a rate — is enforced by the account rather
than by anyone's good behaviour.

That is the version of this work where 4337 stops being a gas story and becomes
the point: an agent holds a key that *cannot* overspend, rather than one that is
merely trusted not to. It is out of scope here, and it is where this goes.

## Rejected

- **Wagmi in the SDK.** Pins its own viem, needs `@tanstack/react-query`, forces
  a `WagmiProvider` above `SettleProvider`. Every host already on Privy, Dynamic
  or RainbowKit would carry two wallet stacks. `PaymentSigner` exists so that
  never happens.
- **CDP managed smart accounts.** `@coinbase/cdp-sdk` exports only `.`, `./auth`,
  `./x402`, has no `browser` field, and requires `apiKeySecret` + `walletSecret`.
  It cannot run in a browser, so it cannot back a burner.
- **`TxHash | UserOpHash` branded union.** The brands are optional phantom
  properties, so an unbranded hex string satisfies both arms and nothing can
  narrow the union at runtime. Cost of a breaking change, none of the safety.
  Mutual exclusion via `?: never` does the job properly; see Commit 2.
- **Fresh key per purchase.** Every abandoned cart strands 0.1 USDC at a dead
  address; ten abandonments empty the demo.
- **Connect-wallet toggle.** Drags in a connector library to demonstrate an axis
  the docs already demonstrate.

## Provenance

Six decisions here came from reading ZeroDev's docs and SDK (`@zerodev/sdk` v5,
MIT). None of it is their code. The `?: never` exclusivity is how they model
EntryPoint 0.6 vs 0.7 return shapes; `BaseError` with `docsPath` is their error
convention; policy-as-data with tagged params is their `Policy` type, which
carries `policyParams` specifically so permissions can be serialized and
rehydrated; the authoring page, the integration matrix and `llms.txt` are their
docs structure; the mandate-as-policy idea is their permissions model applied to
AP2.

Deliberately not taken: the Kernel plugin architecture, the viem client-decorator
generics, and the hosted dashboard. Settle Kit is a payments library, not an
account vendor. Their `KernelValidator` is a `LocalAccount` plus eight methods;
`PaymentSigner` is three fields, and that difference is the product.

One thing worth keeping: their 23 test files carry no mocks and every one needs a
funded testnet key plus two vendor API keys. Core here injects `client` and
`receiptClient`, so `checkout-safety.test.ts` runs offline. Preserve that.
